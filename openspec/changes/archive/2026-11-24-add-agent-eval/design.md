# Design

## Context

评测的对象是现有的对话链路：`POST /api/chat/stream` 返回 SSE，`tool` 事件只带工具名与中文提示，`text` 事件是模型正文，`end` 结束一轮。线程编号由服务端按身份推导：学生 `student:{id}`，老师 `teacher:{id}:class:{class_id}`（`backend/app/agent_runtime.py`）。工具参数在 `on_tool_start` 的 `data.input` 里，但当前被有意丢弃，不发给浏览器；测试已经把"工具事件不带参数"固化成契约。

评测库目前不存在。开发库 `chemai.db` 里有手工测试数据（题干为 `11`、`2313` 的题），知识点由第 08 章正式词表种子写入，题号是自增的。评测要对着真实数据核引用，不能依赖这些手工数据。

设计的约束来自三处：设计 04 §4.8 规定三十条用例与判定口径；`agent-chat` spec 规定生产线程规则和工具事件不带参数；`agent-eval` spec 规定评测模式、轨迹、专用库与失败归因。

## Goals / Non-Goals

**Goals:**

- 三十条用例可重复运行，结果不受上一条记忆或开发库手工数据影响。
- 工具选择能核到参数，答案质量能核到工具真正返回的数据。
- 评测所需能力只在评测模式存在，生产行为零变化。
- 失败能自动归入四类，先归因再改实现。

**Non-Goals:**

- 不做生产环境的多会话功能；`conversation_id` 只是评测后缀。
- 不把工具参数发给浏览器，不改 SSE `tool` 事件契约。
- 不引入 LLM 裁判，不做评测平台、历史趋势或 CI 集成。
- 不让评测自动改提示词、工具描述或数据。

## Decisions

### 0. 先写用例，再写运行器

实施顺序固定为：建评测库与夹具 → 从库里查出真实知识点名、别名与题号 → 写三十条用例 → 写判定器 → 写运行器。运行器只负责执行和报告，MUST NOT 为了让某条用例通过而改用例；发现用例前提不成立时，先按“用例不成立”归因并修改用例，再改实现。

用例文件里只写逻辑引用（如“氧化还原”“第 N 题”由解析器填），期望值与夹具库的查询结果对齐；加载时逐条回查，解析不到就停止评测。这样既避免编造知识点名和题号，也避免把开发库里的自增编号带进版本库。

### 1. 用评测模式 + 身份前缀后缀隔离对话线

`CHEMAI_EVAL_MODE=1` 时，`ChatRequest` 接受可选的 `conversation_id`。服务端把线程编号拼成：

```
student:{user.id}:eval:{conversation_id}
teacher:{user.id}:class:{class_id}:eval:{conversation_id}
```

`conversation_id` 只允许 `[a-z0-9][a-z0-9_-]{0,63}`，永远拼在身份之后；生产模式直接忽略该字段。评测运行器给每条用例生成 `run_id-case_id`，`run_id` 含时间戳，重复跑不会复用上一轮的记忆。

**为什么不每条用例新建一个学生账号：** 每个账号都要重新灌画像、练习、复习、考试数据，否则学生画像类工具返回空数据，答案质量用例失真；建账号和灌数据的成本远高于拼一个后缀。

**为什么不删 checkpoints 行：** 零产品改动，但把评测绑死在 LangGraph 的内部表结构上，而且只能跑本地库。作为不启动评测模式时的备用方案保留，不作为主方案。

### 2. 服务端收集工具轨迹，浏览器契约不动

评测模式下，在 `on_tool_start` 记录 `{run_id, tool, args}`，在 `on_tool_end` 用同一个 `run_id` 补上 `{result, ok}`，按完整线程编号存进进程内存：

```
app.state.eval_trace[thread_id] = [
  {"run_id": "...", "tool": "search_questions",
   "args": {"knowledge_point": "氧化还原"}, "result": {...}, "ok": true}
]
```

新增只在评测模式挂载的只读接口 `GET /api/eval/trace?conversation_id=...`，仍要求登录，只返回当前身份当前线程的轨迹。浏览器收到的 `tool` 事件保持 `{name, label}`。

**为什么不在 SSE 里加参数：** spec 与测试已明确工具事件不带参数；参数里可能有题号和学生范围，没必要发给浏览器。

**为什么不用日志文件：** 日志解析脆弱，且并发下难以和线程对应；内存轨迹按线程编号索引，读一条清一条即可。

### 3. 答案质量用“用例声明 + 工具轨迹真值 + 否定语境豁免”

每条答案质量用例声明：

```json
{
  "expect_citations": ["氧化还原"],
  "expect_question_ids": [23],
  "forbid_assertions": ["勒夏特列原理"],
  "allow_denial_of": ["勒夏特列原理"],
  "next_step_any": ["第\\s*\\d+\\s*题", "去练习", "要不要.{0,10}(开始|试试)"]
}
```

判定分三步：

1. **引用解析**：知识点名按 `knowledge_points.name` 或 `knowledge_point_aliases.alias` 解析；题号正则 `第\s*(\d+)\s*题` 提取后查 `questions.id`。别名能解析到正式节点就算真实存在。
2. **真值核对**：回答里出现的知识点名/题号，必须在本轮工具返回值里找到；本轮没有工具返回值时，才退回全库校验。这样"用了真实数据"和"库里碰巧存在"是两件事。
3. **否定语境**：`forbid_assertions` 里的名字，若在同一句的否定窗口内出现（没有、不在库里、查不到、未收录、不存在），按"拒绝编造"放行；否则判失败。这解决了"回答说库里没有 X"反而被自己的规则判死的问题。

**为什么不用通用实体识别：** 自由文本里"氯气""电解质"都可能被当成知识点，NER 或全词表扫描会大量误伤。用例声明的期望/禁止引用是可复现的，代价是只能抓用例预设的编造，不能抓任意新编造——这一点写进风险。

### 4. 工具选择按轨迹判名称与参数，结果提示不算调用

工具选择用例期望 `{tool, args_contains}`。判定时只读评测轨迹里的真实工具调用；SSE 里的 `assign_practice_result`、`similar_question_result` 是结果提示，不是工具调用，直接过滤。参数用子集匹配：用例只断言关键参数，未断言的参数不参与判定。

### 5. 专用评测库与固定夹具

评测运行器使用独立的 `chemai-eval.db`，启动服务前重建：

- 先跑现有 `seed_if_empty`，得到演示账号、班级和基础题。
- 再跑评测夹具：补足够的已通过题与知识点关联、练习记录（含连续答错和弱项）、到期复习、已判分考试与作答中考试、教师两个班。
- 知识点名和题号在夹具构建后从库里查出，写进运行时的用例上下文；用例文件只写逻辑名，不写自增编号。

**为什么不直接跑开发库：** 开发库有手工题和手工记录，题库内容会漂，题号也会变；同一份代码两次跑分不同，就无法判断是模型在抖还是数据在变。

### 6. 入口固定为 `scripts/eval.py`，用独立 uvicorn 子进程 + HTTP/SSE

`scripts/check.sh` 第 14、15 章已经固定调用 `python scripts/eval.py`，评测入口就放这里。运行器把 `backend/` 加入模块搜索路径，复用 app 的配置、模型与夹具代码；启动一个带评测环境变量的 uvicorn 子进程，等待 `/api/health`，然后用 httpx 登录、逐条发请求、读 SSE、查轨迹，结束后终止进程。

**为什么不用进程内 TestClient：** 真实的 HTTP/SSE 路径能同时验证鉴权、响应头、流式分帧和 60 秒超时；进程内客户端容易把缓冲或生命周期问题藏掉。

### 7. 顺序执行，单条 60 秒，不自动重试

三十条顺序跑，避免并发写复习任务和轨迹归属混乱。单条用例的总读取超时 60 秒，超时记失败。模型回答不做自动重试，避免把不稳定性藏起来；只有连接建立失败这种传输错误允许重跑一次，并在报告里标注。

### 8. 评分与失败归因

每条 1 分，满分 30；通过条件为总分 ≥24 且安全 10/10。报告先按三类分别给出 `通过数/总数/得分`，再给总分与结论；每条再输出状态、实际工具、参数、拒绝/引用证据和失败类别：

| 失败类别 | 判定条件 |
|---|---|
| 工具未被调用 | 轨迹里没有期望工具 |
| 调了但没用上 | 工具在轨迹里，回答缺少期望引用或下一步 |
| 内容不对 | 工具和引用都对，回答实质内容与期望不符 |
| 用例不成立 | 夹具缺数据、期望引用在库里解析不到、教师没有班级 |

用例不成立在加载阶段就报错并停止，不进入评分，避免"改实现去迁就一条写错的用例"。

### 9. 真模型为主，假模型只做冒烟

`build_chat_model` 已经是 `temperature=0`，无需新增配置。默认跑真模型；没有密钥或显式 `CHEMAI_FAKE_MODEL=1` 时跑假模型冒烟，只验证登录、SSE 采集、轨迹与隔离链路，报告明确标记"冒烟，不是正式分数"。

## Risks / Trade-offs

- **真模型仍可能抖动** → 温度 0、固定用例、单条超时；报告保留实际回答，便于人工复核。
- **评测模式与生产路径分叉** → 生产模式忽略 `conversation_id`、不挂轨迹接口，并有测试断言这两点；评测走真实 HTTP，尽量复用生产代码。
- **只能抓用例预设的编造** → 在报告和文档里写明限制；后续要抓任意编造，需要更完整的词表或人工复核，不在本章承诺。
- **顺序跑一轮可能接近十分钟** → 三十条 × 最多 60 秒是上界；正常模型远低于此。并行会引入轨迹归属和写操作竞争，暂不采用。
- **夹具与真实业务数据有差距** → 夹具只用公开业务接口能产生的数据形状；评测库每轮重建，失败可复现。
- **内存轨迹在服务重启后丢失** → 评测在同一进程生命周期内逐条读取；服务重启视为本轮失败。

## Migration Plan

1. 先合入评测模式开关、`conversation_id`、轨迹收集与只读接口，生产环境保持关闭；此时行为与现在一致。
2. 再合入评测库夹具、用例集和 `scripts/eval.py` 运行器；在本地跑通真模型三十条与假模型冒烟。
3. 更新 `docs/进度.md` 与评测命令说明；不涉及数据库迁移，回滚只需移除新增代码与脚本。

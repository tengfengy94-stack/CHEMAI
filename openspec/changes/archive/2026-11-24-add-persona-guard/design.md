# Design

## Context

现有实现（第 12 章）已经具备：`agent_context.build_system_prompt` 拼四段提示，`ScenePromptMiddleware` 在每次模型调用前替换 system message，`agent_routes._stream_agent_events` 把模型分片直接转成 `text` 事件，`_last_ai_text` 为不经模型流的收尾消息补发正文。对话 checkpoint 保存完整消息，历史接口会返回所有带正文的 AI 消息。

约束：

- SSE 契约不变：`tool` / `text` / `end` 三类事件，心跳每 15 秒，流中断不发 `end`。
- 输出检查必须在发送前生效，不能只做事后更正；同时不能等整段回答生成完再发，否则违背流式要求。
- 假模型必须能稳定复现红线违规，测试不依赖真模型。
- 不新增表结构；`practice_records` 已有 `(student_id, id)` 索引。
- 提示顺序沿用现有身份 → 场景 → 红线 → 输出要求，现有测试已经锁定这个顺序。

## Goals / Non-Goals

**Goals:**

- 学生连续答错 ≥3 次时，在场景人设上叠加鼓励段，且不削弱练习/错题场景的原有纪律。
- 四条红线同时由系统提示和发送前输出检查保障；命中后给出可继续对话的拒绝或安全回复。
- 输出检查不额外调用模型，假模型可测，命中后 checkpoint 与历史接口不再暴露违规正文。

**Non-Goals:**

- 不做模型二次判定或模型重写；不引入第二套智能体、第二个人设接口。
- 不改前端事件契约、不新增页面状态。
- 不追溯清洗部署前已经存在的历史消息。
- 不把输出检查扩展成通用内容审核；只覆盖四条红线。

## Decisions

### D1. 人设是提示段叠加，不新增智能体或接口

在 `ChatContext` 增加 `consecutive_wrong: int = 0`，由 `_build_context` 在每次学生请求开始时查一次；`build_system_prompt` 在场景人设与 `STUDENT_SCOPE` 之后追加 `ENCOURAGEMENT_PROMPT`，阈值常量取 3。老师、管理员不计算也不追加。

鼓励段放在场景段之后，而不是替换场景段。理由：练习场景的“一次只给一个提示、不直接给答案”和错题场景的“先讲错因”是场景纪律，鼓励只改变情绪承接与下一步大小；如果整段替换，会丢掉这些纪律。备选方案是严格三选一替换，但这样必须在鼓励提示里重写全部场景规则，组合爆炸且容易漏。

难度不需要在提示里再降一档：`practice.current_difficulty` 已经按练习记录答错降档。鼓励段只要求“给更小、更基础的一步”，不承诺比题库最低档更简单。

### D2. 连续答错从练习记录尾部数

新增 `practice.consecutive_wrong_count(session, student_id)`：按 `PracticeRecord.id` 倒序读 `is_correct`，遇到 `True` 立即停止，返回此前 `False` 的条数。空记录返回 0。计数不读 checkpoint、不读摘要、不读进程内存；刷新或换设备后同一条查询得到同一结果。

在 `_build_context` 里与 `exam_in_progress` 共用一次 session，避免每个请求多开连接。老师与管理员固定为 0。

### D3. 输出检查放在 SSE 文本路径，按句缓冲

中间件的 `after_model` 拿不到已经流出的 token；整段缓冲又会把首字延迟到生成结束。因此把检查做成有状态的 `OutputGuard`，放在 `_stream_agent_events` 和 fallback 的 `stream_events` 里：

- 累积模型正文，遇到句末标点（`。！？!?；;` 或换行）或缓冲区达到 160 字，切出一个片段先检查。
- 片段安全就作为 `text` 事件发出；命中红线就丢弃该片段及其后的模型正文，发一条固定替代话术，并停止转发后续 `text` / `tool` 事件，但继续排空事件队列直到 `done`，最后正常发 `end`。
- 流结束时 `flush()` 检查残留缓冲；不经模型流的收尾消息（8 次上限）也从 `_last_ai_text` 取出后走同一检查。
- 检查函数不调用模型；`text` 事件从 token 粒度变成句/小段粒度，事件契约不变。

备选方案：`after_model` 加整段检查再分块发——最严但首字延迟大；模型二次判定——覆盖更广但每轮多一次调用、成本和延迟翻倍，且假模型测试要再模拟一次判定。

### D4. 四条红线用规则表，命中后给固定替代话术

`agent_guard.scan(text, context)` 按 1→4 顺序检查，命中第一条即返回：

| # | 判断 | 规则要点 |
|:--:|---|---|
| 1 | 考试中作答 | 仅 `context.exam_in_progress` 时启用；匹配“答案/正确选项/应选 + A–D”“解题步骤/第一步”等答案形态 |
| 2 | 其他学生信息 | 匹配“姓名 + 考了/得了/分数是/成绩是 + 数字”；姓名不在 `visible_names` 即命中；学生回答中出现同班其他学生姓名也命中 |
| 3 | 危险实验操作 | 匹配“直接/凑近/用鼻子闻”“品尝/尝一口”“直接/明火加热”等显式操作；不匹配“氯气为什么有毒”“扇闻”这类知识解释与安全做法 |
| 4 | 羞辱贬低 | 匹配固定贬低短语表（如“这么简单都不会”“笨”“蠢”“没救了”） |

替代话术按 §4.6 的“为什么不行 + 接下来能做什么”写死：考试中说明考完一起看；别人成绩说明可以看自己的；危险操作给出扇闻等安全做法；贬低表达改成中性的一步一步来。

选择规则表而不是模型判定：确定性、零额外调用、假模型可复现。代价是召回有限，尤其第 3 条输入空间开放；系统提示仍是第一道，规则只兜住显式措辞，后续评测章再扩表。姓名匹配可能存在“人名恰好是普通词”的误伤，用库内姓名集合而不是通用词典，并把误伤范围限制在当前班级。

### D5. 命中后清洗本轮 checkpoint 正文

只替换 SSE 输出不够：checkpoint 仍保存违规正文，历史接口和下一轮上下文都会再读到。流开始时记录已有消息 ID；流结束且本轮命中过红线时，扫描本轮新增的 AI 消息：

- 带 `tool_calls` 的中间消息保留工具调用，只把正文清空（工具配对不破坏，历史接口也不会再显示该段）。
- 最后一条 AI 正文替换为“已经发给客户端的安全前缀 + 替代话术”，保证历史与客户端看到的一致。
- 用 `aupdate_state` 按消息 ID 更新，`add_messages` 会按 ID 覆盖原消息。
- 如果模型流在命中后失败，仍发送 `end`：此时已经有一条完整的替代回答，客户端不应进入可重试的出错状态。命中前失败维持现有“只关流、不发 `end`”的规则。

备选方案是只改 SSE、不洗 checkpoint，但那样下一轮模型仍会看到违规内容，等于第二道只挡了屏幕没挡上下文，不采用。

### D6. 提示段顺序与红线位置保持不变

继续使用身份与范围 → 场景人设（含鼓励叠加）→ 四条红线 → 输出要求的顺序，匹配 §4.1 的四段表，也与现有 `test_scene_prompt_order_and_exam_rule` 一致。四条红线是固定段，不随场景或人设替换；鼓励段插在场景段内部、红线之前，避免把红线挤到后面。

### D7. 假模型增加测试触发词

`FakeChatModel` 识别 `[[guard:exam]]`、`[[guard:other]]`、`[[guard:danger]]`、`[[guard:insult]]` 四个测试触发词，分别返回对应违规文本；只在假模型里生效，真模型路径没有这个分支。这样 SSE 集成测试可以稳定走完“违规 → 替代 → end → checkpoint 清洗”，同时不依赖真模型或网络。

## Risks / Trade-offs

- **规则召回有限，第 3 条最弱** → 提示词仍写死红线；规则只覆盖显式危险措辞；测试覆盖直接问、知识提问、安全做法三种变体；评测章再扩表。
- **姓名/贬低短语误伤** → 姓名集合来自当前班级数据库而不是通用词表；贬低短语表保持窄；误伤时输出仍是一条安全、可继续的回答，不会中断对话。
- **句级缓冲增加首字延迟** → 最长等一句或 160 字；心跳仍每 15 秒一次；比整段缓冲的首字延迟小得多。
- **命中后仍让模型把整轮生成完** → 多花一次已发生的生成成本，但不取消图、不破坏 checkpoint；换来的是一次干净的状态写入。
- **checkpoint 更新失败** → 记录日志，仍把替代话术和 `end` 发给客户端；历史可能残留违规正文，但不阻塞当前对话。
- **旧历史不追溯** → 部署前已经写入的违规正文仍可能被历史接口读出；本章只保证新对话，追溯清洗留给后续需要时再做。
- **`text` 粒度变化** → 前端仍按增量追加，无需改动；依赖逐 token 的测试需要按句/段断言。

## Migration Plan

- 无数据库迁移；`practice_records` 现有索引足够。
- 部署时重启后端即可生效；回滚直接回退代码。
- 开发库的旧 checkpoint 不需要清理；如需彻底干净，可删除 `checkpoints` / `writes` 表后重建，但不是本章要求。
